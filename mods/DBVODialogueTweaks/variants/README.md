# UI-overhaul compatibility variants

A **variant** is this mod's `dialoguemenu.swf` deltas re-applied on top of a UI overhaul's *own*
DBVO-patched `dialoguemenu.swf`, so a user of that overhaul keeps their dialogue layout and still
gets the mod. Only the swf differs — the `.esp`, both `.pex` and the DLL are shared, because every
base keeps Bethesda's `_root.DialogueMenu_mc` path, which is all the DLL
(`dbvoOnPlayerLineEnded`) and the MCM (`dbvoPadMs`) ever address.

Why this exists: the first Nexus feedback on the mod was *"my dialogue options moved from the left
to the right"* — our stock-DBVO-layout swf had overwritten the user's overhaul-patched one. The
landscape (who ships a DBVO 1.x patch, where, how popular) is in
[`docs/dbvo-landscape.md`](../../../docs/dbvo-landscape.md).

Each menu design is its author's work and is shipped under that mod's own Nexus permissions
(checked 2026-09-09, Vel'dun 2026-09-19 — all permit reuse with credit; credit is given on the mod page, in the mod README
and in the installer's own description for each style). A new variant is only mechanical once its
mod's permissions have been read the same way.

Each `variants/<id>/` holds:

- `variant.conf` — `key=value` metadata: display name, install order, the base's md5, where the
  base came from. Read by `build.sh`, `package.sh` and `port.sh`; **the variant list is the
  directory listing**, so adding one is a new directory and no edit anywhere else.
- `base.swf` — the UI mod's DBVO-patched menu, **committed** under that mod's permissions (as
  DBVO's own swf is), so a clone builds every variant without a manual download. **Except
  Vel'dun's**, which are git-ignored: its page allows modifying and releasing with credit but
  forbids uploading its files "to other sites", and this repo is public on GitHub. To refresh one or
  add another: download from the `source=` URL in `variant.conf`, take the `dialoguemenu.swf` out
  of the archive (the path differs per archive — see `base_file=`) and save it as `base.swf`.
  `build.sh` skips a variant whose base is missing and `package.sh` refuses to release without it;
  a base whose md5 no longer matches `base_md5=` is a hard error, because the committed port was
  merged against that exact file.
- `script_from=<id>` (optional, in `variant.conf`) — for a UI mod that ships **no** DBVO-patched
  menu but whose `DialogueMenu` class is another variant's, unchanged: `port.sh` merges against
  *that* variant's DBVO-patched script, and `build.sh` still imports the result into this
  variant's own `base.swf`. Vel'dun uses it (below).
- `src/__Packages/DialogueMenu.as` — **generated by `port.sh`, committed**, so the build never
  depends on the porter and a port is reviewable as a diff.

## Re-porting

```bash
./variants/port.sh              # re-port every variant
./variants/port.sh untarnished  # just one
./variants/port.sh --verify     # check the committed ports still carry every delta
```

`port.sh` is a three-way merge — base = stock DBVO's decompiled script, *ours* = `src/`, *theirs* =
the variant's decompiled script — so **the deltas live in exactly one place** (`src/__Packages/
DialogueMenu.as`) and a feature added there is never silently missing from a variant.

Two things it does beyond the merge:

- **The `timerBool` fixup.** Every third-party patch dropped stock DBVO's `this.timerBool = false;`
  from `startTopicClickedTimer`'s `voicePackID == "off"` branch. Without it a topic click with the
  voice off leaves `timerBool` true forever, `DoShowDialogueList` becomes a no-op and the topic list
  never comes back. `port.sh` restores it; `check_offbranch` in `lib.sh` proves it survived into the
  built swf.
- **Marker checks.** `ffdec -importScript` exits 0 whether or not it actually replaced the class, so
  every build decompiles its own output and greps for each delta. A silently unpatched swf is
  indistinguishable, in play, from the mod not being installed — this is the check that catches it.

**One conflict is expected, on every CDUI-lineage base** (`untarnished`, `dddm-white`,
`dddm-warm`, both `veldun`s): they set `TextCopy_mc.textField._y = 3.75 - _loc3_` where stock DBVO sets `6.25`, and
our `skse.SendModEvent("CutNpcDBVOReply","")` line is added right after it. **Resolve by keeping
their offset and taking our line** — the offset is the UI mod's own layout, never ours. `port.sh`
writes the conflicted file next to the target as `DialogueMenu.as.conflict` and tells you the rest.

## Vel'dun: a UI mod with no DBVO patch

Vel'dun UI dropped its DBVO patch in 1.0.6 ("no longer needed with DBVO 2 or Dragonborn
ReVoiced"), so neither of its two dialogue menus has DBVO's hooks. But its `DialogueMenu` class is
Dear Diary Dark Mode's (it ships DDDM's `deardiary_dm/` assets and config) — decompiled, it differs
from DBVO's own *DDDM white* patch only in DBVO's hunks and ffdec register renumbering, and every
other class in the swf is byte-identical. So DBVO's DDDM patch **is** its DBVO patch:
`script_from=dddm-white`, and both Vel'dun ports come out byte-identical to `dddm-white`'s. Only the
swf they are imported into differs — Vel'dun's frames, fonts and layout. The ESO swf also differs
in `gfx/managers/InputDelegate`, which the import never touches.

That claim was checked against the exact `base_md5` in each `variant.conf`. A newer Vel'dun fails
that md5 check, and whoever moves the base must re-check that its `DialogueMenu` is still DDDM's
before re-porting. If it isn't, the fallback is merging with Bethesda's vanilla `DialogueMenu` as the
base (from `Skyrim - Interface.bsa` via `tools/BsaExtract`); tried here, that gives 8 mechanical
conflicts.

## Adding another

1. `mkdir variants/<id>` and drop in the UI mod's DBVO-patched swf as `base.swf` (no DBVO patch
   for it anywhere? see the Vel'dun section — decompile and compare against the existing bases).
2. Write `variant.conf` (copy a neighbour; `base_md5` from `md5sum`, `order` = where it belongs in
   the installer list).
3. `./variants/port.sh <id>` — resolve any conflict as above.
4. `./build.sh` then `./package.sh` — it appears in the FOMOD's "Dialogue menu style" group.
5. Verify it in-engine: `./stage-test-profile.sh --variant <id>` then the replay in the mod
   README's *Testing* section. A variant is not done until the reply-on-line-end assertion passes
   against *its* swf.

The priority order for further overhauls (Dialogue Interface ReShaped, Convenient Dialogue UI's
four looks, Dragonborn Reskin) is in `docs/dbvo-landscape.md`.

## Do not strip these from a ported menu

Whatever the overhaul's own script looks like, a ported `dialoguemenu.swf` must keep all of this.
Each one is load-bearing and none of it is obvious from reading the diff:

- **`bAllowProgress`, `SkipText`, `ALLOW_PROGRESS_DELAY`, and the `startTopicClickedTimer` `"off"`
  branch.** The `"off"` branch is the voice-pack-disabled path: with no DBVO voice for a line it must
  still fire `TopicClicked` directly, or dialogue stops advancing for anyone who has a voice pack
  switched off. A port that "cleans up" these symbols passes the reply-on-line-end test and breaks
  that path silently, because the test always runs *with* a voice pack.
- **The double-fire guard.** `topicClicked()` guards its state via `timerBool`, and calling it twice
  must stay impossible: `trySkipPlayerLine` clears `this.timer` / `timerBool` before calling, so the
  already-scheduled callback cannot also fire.
